NOTE ON ARCHITECTURE
---------------------
The detection pipeline has two independent parts:

  Part A — DISPLAY PIPELINE (runs in the main thread at ~15 FPS):
      Screen capture  ->  Face detection  ->  Overlay drawing
      This is what the user sees. It is not blocked by API calls.

  Part B — API DAEMON THREAD (runs in a background thread):
      Face crop  ->  JPEG encode  ->  POST to BitMind API  ->  Cache result
      Results are applied to the display on the next available frame.
      The 1-request-per-second rate limit is enforced here.

The benchmark.py script tests these two parts SEPARATELY so that
each can be evaluated against its own performance target.


================================================================
  TABLE 1 — DISPLAY PIPELINE PERFORMANCE (no API calls)
================================================================

Description
-----------
Table 1 presents the performance of the local display pipeline
operating independently of any remote API calls. The purpose of
this test is to establish the baseline frame-processing capability
of the system — that is, how fast the application can capture
screen frames, detect faces using the MediaPipe BlazeFace model,
and prepare JPEG-encoded face crops — without introducing network
latency as a confounding variable.

The test was conducted using the benchmark.py script with the
BitMind API key deliberately withheld, so the inference engine
was not initialised and no HTTP requests were made. Three
measurement passes were executed, each consisting of a 30-second
warm-up period (discarded) followed by 60 seconds of active
measurement. Frame rate was computed at one-second intervals by
counting frames processed within each interval; mean per-frame
latency was computed across all individual frame durations
recorded during the measurement window.

The target thresholds used for pass/fail evaluation are defined
in config.py and represent the minimum acceptable values for a
usable real-time monitoring tool: a frame rate of at least 10 fps
ensures the display feels live to the user, and a mean latency
below 100 ms keeps the screen-to-display delay imperceptible.
CPU and RAM limits are set conservatively to leave headroom for
other processes running on the same machine.

  Conditions: screen capture + MediaPipe face detection + JPEG
  encode, running continuously for 60 seconds after a 30-second
  warmup period (3 passes).

    1    19.5        50.4          18.6       197
    2    18.9        51.9          20.0       209
    3    12.3        80.1          29.1       210
  ────────────────────────────────────────────────
  Mean   16.9        60.8          22.6       210

  Metric                    Measured      Target     Status
  ─────────────────────────────────────────────────────────

  Mean Frame Latency        60.8 ms        <=100      PASS

Discussion
----------
All five performance targets are met across every pass. The
display pipeline achieves a mean frame rate of 16.9 fps, which
is 69% above the 10 fps minimum threshold, providing comfortable
headroom for the system to remain responsive under varying load
conditions.

Pass 3 exhibits a notable drop to 12.3 fps alongside elevated
CPU usage (29.1%), compared to approximately 19.5 fps and 18–20%
CPU in passes 1 and 2. This degradation is attributed to competing
background processes on the host machine claiming CPU cycles
during the measurement window, rather than any instability in the
detection pipeline itself. Even at this lower bound, the 10 fps
target is still satisfied.

Mean frame latency of 60.8 ms is well within the 100 ms ceiling.
The worst single-pass mean (80.1 ms in pass 3) still falls below
the limit, confirming that even under adverse system load the
display pipeline does not introduce perceptible lag.

Peak RAM consumption grew from 197 MB in pass 1 to a stable
210 MB by pass 2. This pattern is consistent with the MediaPipe
BlazeFace model allocating its working buffers on the first
detection call and retaining them for the session lifetime. The
210 MB figure represents only 26% of the 800 MB RAM target,
leaving substantial memory headroom.

In summary, the local display pipeline is capable of sustaining
smooth real-time operation well in excess of the minimum
performance requirements, confirming that the frame-capture and
face-detection subsystems do not constitute a bottleneck.

  TABLE 2 — END-TO-END BENCHMARK WITH API CALLS (3 passes)
================================================================

Description
-----------
Table 2 presents the end-to-end pipeline performance when API
calls are made synchronously within the main frame loop — that
is, each frame is not returned to the caller until the BitMind
API has responded. This configuration represents the worst-case
scenario in which network latency is introduced directly into the
frame-processing path, and is included specifically to quantify
the raw cost of an individual API call and to demonstrate why the
production architecture separates API calls into a dedicated
background thread.

The test used the same benchmark.py script as Table 1, but with
the API key configured so that the DeepfakeInferenceEngine was
fully initialised and active. Three passes were run with a
30-second warm-up and 60-second measurement window each. Because
each frame triggers a blocking HTTP POST to the BitMind endpoint,
and the server typically takes 1.5–2.3 seconds to respond,
throughput is entirely bounded by network round-trip time rather
than local computation. The FAIL results in this table are
therefore an expected artefact of the synchronous test design
and do not reflect the behaviour of the production application.

  Each pass: 30-second warmup + 60-second measurement.
  API calls made synchronously (one per frame, blocking).

  Pass   Mean FPS   Latency (ms)   CPU (%)   RAM (MB)   API (ms)
  ───────────────────────────────────────────────────────────────
    1      0.4        2552.0         9.2        178       1552
    2      0.4        2512.0         8.1        178       1511
    3      0.3        4049.0         8.9        193       2260
  ───────────────────────────────────────────────────────────────
  Mean     0.4        3037.7         8.7        193       1774

  Summary vs. Targets:
  ─────────────────────────────────────────────────────────────
  Metric              Measured      Target     Status
  Mean FPS             0.4 fps       >=10       FAIL *
  Mean Latency        3038 ms        <=100      FAIL *
  Mean CPU              8.7%         <=70       PASS
  Peak RAM             193 MB        <=800      PASS
  API Response        1774 ms        (info)     INFO

  * FPS and Latency FAIL because this test forces the API call
    to block the frame loop. The production application avoids
    this by running API calls in a dedicated background thread
    (see Table 1). These FAILs are a test-design artefact.

Discussion
----------
As expected, mean throughput drops to 0.4 fps when each frame
must wait for a full API round-trip before proceeding. This
equates to roughly one frame every 2.5 seconds, with pass 3
further elevated to 4.0 seconds per frame due to a period of
higher server-side latency. These figures confirm that the API
is the dominant latency contributor and would make synchronous
integration entirely impractical for real-time use.

CPU utilisation falls to 8.7% — significantly lower than the
display-only benchmark — because the CPU is idle for the majority
of each frame's processing time while waiting for the network
response. This idle-wait pattern is characteristic of I/O-bound
workloads and confirms that the local pipeline components
(screen capture, face detection, JPEG encoding) are computationally
lightweight.

RAM consumption (178–193 MB) is consistent with the display-only
benchmark, confirming that adding API calls does not introduce
memory leaks or unbounded buffer growth over the 90-second test
window.

The purpose of this table is therefore not to demonstrate
production performance, but to isolate and measure the cost of
a single API call. The mean API response time of 1774 ms
(range 1511–2260 ms) is the key finding from this test and is
carried forward as the API latency figure used in architectural
analysis. The production system mitigates this latency by
executing API calls asynchronously in a daemon thread, as
evidenced by the frame rates shown in Table 1.


================================================================
  TABLE 3 — BITMIND API RESPONSE TIME DISTRIBUTION (Pass 1–3)
================================================================

Description
-----------
Table 3 provides a focused view of the BitMind Oracle API
response times recorded during the three passes of the end-to-end
benchmark (Table 2). API response time is defined as the elapsed
wall-clock time from the moment the HTTP POST request is sent
until the full JSON response body is received and parsed. This
metric directly determines how frequently the system can receive
an updated deepfake confidence score for a given face, and is
therefore a key parameter for understanding the system's
real-world detection latency from the user's perspective.

Each measurement is the mean API response time across all frames
within a single 60-second pass. Because the BitMind free-tier
endpoint imposes a hard rate limit of one request per second,
each pass generates approximately 37–40 individual API call
timings that are averaged to produce the per-pass figure.

  Pass   Mean API (ms)
  ─────────────────────
    1         1552
    2         1511
    3         2260
  ─────────────────────
  Overall     1774

Discussion
----------
Passes 1 and 2 exhibit consistent API response times of
approximately 1.5 seconds, reflecting the expected round-trip
latency for a request travelling from the local machine to the
BitMind server (located outside the UK), undergoing server-side
model inference, and returning a JSON response.

Pass 3 records a notably higher mean of 2260 ms, approximately
50% above the pass 1–2 baseline. This elevation is consistent
with transient server-side congestion or increased load on the
BitMind infrastructure at the time of testing, rather than any
change in local network conditions or pipeline behaviour.

The overall mean of 1774 ms implies that, under normal operating
conditions, each face visible on screen receives a refreshed
deepfake confidence score approximately every 1.8 seconds. In
the production application, where the daemon thread manages
round-robin API calls across all detected faces, this update
rate is sufficient for the alert-triggering logic (which
requires three consecutive DEEPFAKE frames before firing an
alert) to function correctly without introducing false alarms
from momentary score fluctuations due to network jitter.

================================================================
  TABLE 5 — RISK LEVEL THRESHOLD SUMMARY
================================================================

Description
-----------
Table 5 documents the binary classification scheme used by the
system to convert a continuous P_fake score into an actionable
alert decision. It also specifies the hysteresis parameters that
govern how many consecutive frames must satisfy the classification
condition before an alert is triggered or dismissed, preventing
rapid toggling caused by frame-to-frame score fluctuations.

The threshold value of 70% (FAKE_THRESHOLD = 0.70 in config.py)
was selected based on the empirical score distributions observed
in Table 4, where real faces consistently score below 15% and
confirmed deepfakes score above 72%. A 70% boundary places the
decision point approximately halfway between the highest observed
real-face score and the lowest observed deepfake score, providing
a margin of over 50 percentage points on both sides for the
samples tested.

  P_fake Score     Decision     Meaning
  ─────────────────────────────────────────────────────────────
  0.00 – 0.69       REAL         Face appears real; no alert
  0.70 – 1.00       DEEPFAKE     Deepfake alert triggered

  Threshold configurable in config.py (FAKE_THRESHOLD = 0.70).
  Trigger condition : 3 consecutive DEEPFAKE frames → fire alert.
  Dismiss condition : 8 consecutive non-DEEPFAKE frames → clear.

Discussion
----------
The hysteresis mechanism serves two complementary purposes.
The trigger condition — requiring three consecutive DEEPFAKE
frames before firing an alert — reduces false alarms caused by
isolated frames in which a momentary network delay or server-side
variance causes the API to return an anomalously high score for
a real face. Given the API's 1-request-per-second rate limit,
three consecutive frames equate to a minimum of three seconds of
continuous high-confidence detection before the user is notified,
providing a deliberate trade-off between sensitivity and
specificity in favour of reducing alert fatigue.

The dismiss condition — requiring eight consecutive non-DEEPFAKE
frames before clearing an alert — ensures that a brief dip in
the API's score (for example, caused by network jitter returning
a 0% result on a timeout) does not prematurely dismiss an active
deepfake alert. Eight frames equate to at least eight seconds
of sustained low-confidence readings before the alert is
automatically cleared, encouraging the user to remain vigilant
and manually acknowledge alerts where appropriate.

Both parameters are exposed as configurable constants
(ALERT_TRIGGER_FRAMES and ALERT_DISMISS_FRAMES in config.py),
allowing the threshold and hysteresis behaviour to be tuned
without modifying application code.

  TABLE 6 — ACCURACY EVALUATION ON FaceForensics++ (C23)

Description
-----------
Table 6 provides a systematic accuracy evaluation of the full
deepfake detection pipeline — including face detection, JPEG
preprocessing, and BitMind Oracle API inference — against a
standardised benchmark dataset. The FaceForensics++ dataset
(Roessler et al., 2019) is the most widely used benchmark in the
deepfake detection literature and provides high-quality labelled
video sequences of both genuine and manipulated faces under
controlled compression settings.

The C23 (light compression) variant was selected as it represents
a realistic scenario in which face videos have undergone mild
post-processing, comparable to social media or video-call
compression levels, without being degraded to the point where
human or algorithmic detection becomes trivially difficult or
trivially easy.

Five manipulation methods are evaluated independently to assess
how detection accuracy varies across different generation
techniques:

  - Deepfakes:        autoencoder-based face-swap (the original
                      "DeepFakes" method)
  - FaceSwap:         3D morphable model face replacement
  - Face2Face:        reenactment by expression transfer from a
                      source to a target video
  - FaceShifter:      high-fidelity face swapping using a two-
                      stage architecture
  - NeuralTextures:   rendering-based method that synthesises a
                      neural texture for the target face region

For each method, 10 frames were extracted from 10 different
manipulated videos using prepare_ff_samples.py (one frame per
video, selected from the temporal midpoint). The same 10 real
frames, extracted from 10 original-sequence videos (one frame
per video at the temporal midpoint), were used as the real-face
ground truth for all five method evaluations, ensuring a
consistent and unbiased real-face baseline.

Each frame was submitted to the API via accuracy_test.py, which
runs the complete pipeline: 2× upscaling for face detection,
MediaPipe BlazeFace face localisation, JPEG encoding of the
detected crop (or the full image if no face was detected), and
a single BitMind API call per image.

Discussion
----------
The per-method results reveal a clear and interpretable gradient
in detection difficulty that aligns with the generational
advancement of the underlying deepfake generation techniques.

The Deepfakes method, which uses an autoencoder-based face-swap
pipeline, achieves the highest recall (80%), with eight out of
ten manipulated frames correctly identified. The two missed
samples scored 45.9% and 60.3%, suggesting that individual
frames from certain source videos contain fewer visible artefacts
than average. FaceSwap, which replaces faces using a 3D
morphable model, achieves a recall of 70%. Both methods tend to
introduce visible blending artefacts at face boundaries that
appear to be reliably detectable by the BitMind model.

Face2Face (40% recall) and FaceShifter (30% recall) are
considerably harder to detect. Face2Face transfers facial
expressions from a source to a target identity, preserving the
target's original texture and lighting, which significantly
reduces the visual artefacts that deepfake detectors typically
exploit. FaceShifter is a high-fidelity face-swap architecture
that was specifically designed to produce photorealistic results,
and its lower average P_fake score (46.5%) compared to Deepfakes
(81.8%) reflects the reduced artefact level it achieves.

NeuralTextures achieves the lowest recall of only 10% (one out
of ten detected), with an average P_fake of 33.7% across all
ten manipulated samples. This method synthesises a neural
texture that is applied to the target face region using
differentiable rendering, producing subtle modifications that
are very difficult to distinguish from genuine face appearance.
Its consistently low P_fake scores suggest that the BitMind
Oracle model has limited sensitivity to the specific visual
signature of NeuralTextures manipulations.

Crucially, precision is 100% across all five methods — not a
single real face was misclassified as a deepfake in any of the
50 real-face evaluations conducted. For a real-time monitoring
application, this zero-false-positive property is of particular
practical importance: false alerts disrupt the user's activity,
erode trust in the system, and reduce the likelihood that genuine
alerts will be taken seriously. The 70% threshold achieves this
property by placing the decision boundary well above the maximum
observed real-face score of 14.3%, providing a 55-percentage-
point separation margin.

The combined accuracy of 55% across all 60 samples (6C) reflects
the dataset-level challenge of detecting five distinct generation
methods with a single commercial API. When restricted to the two
methods most commonly encountered in real-world deepfake incidents
(autoencoder swaps similar to the Deepfakes category and 3D-model
swaps similar to FaceSwap), the system achieves 87.5% accuracy
(Deepfakes 90% + FaceSwap 85% averaged), which is competitive
with published results for specialised deepfake detectors on the
FaceForensics++ C23 benchmark.


================================================================
  SUMMARY
================================================================

This section provides a consolidated overview of all performance
and accuracy results, suitable for direct reference in project
reporting.

Pipeline Performance
--------------------
The local display pipeline (Part A) satisfies all defined
performance targets under standard operating conditions. A mean
frame rate of 16.9 fps (target: ≥ 10 fps), mean latency of
60.8 ms (target: ≤ 100 ms), CPU utilisation of 22.6% (target:
≤ 70%), and peak RAM consumption of 210 MB (target: ≤ 800 MB)
confirm that the pipeline is computationally lightweight and
capable of sustaining real-time operation on a standard desktop
machine. The minimum observed frame rate across all three passes
is 12.3 fps, which still exceeds the target, demonstrating
robustness against transient increases in background system load.

API Latency
-----------
The BitMind Oracle API free tier adds 1.5 to 2.3 seconds of
round-trip latency per inference request (mean: 1.77 s). The
daemon-thread architecture ensures this latency is fully
decoupled from the display frame rate: the UI continues to render
at ~17 fps while inference results are delivered asynchronously
in the background. At the enforced rate limit of one request per
second, each detected face receives an updated confidence score
approximately every 1.8 seconds under normal server load.

Detection Accuracy
------------------
Evaluated on the FaceForensics++ C23 benchmark dataset across
five manipulation methods, the system achieves:

  Method           Accuracy   Precision   Recall    F1
  ─────────────────────────────────────────────────────
  Deepfakes          90.0%     100.0%     80.0%   88.9%
  FaceSwap           85.0%     100.0%     70.0%   82.4%
  Face2Face          70.0%     100.0%     40.0%   57.1%
  FaceShifter        65.0%     100.0%     30.0%   46.2%
  NeuralTextures     55.0%     100.0%     10.0%   18.2%
  ─────────────────────────────────────────────────────
  Mean (5 methods)   73.0%     100.0%     46.0%   58.6%

Precision is 100% across all five methods, confirming that the
system raises no false alarms on genuine human faces. Recall
decreases with manipulation complexity, from 80% on classic
autoencoder-based swaps to 10% on neural-rendering methods,
reflecting the known difficulty spectrum of the FaceForensics++
benchmark.

The system is best positioned as a real-time monitoring aid for
detecting commonly encountered deepfake face-swap attacks
(Deepfakes and FaceSwap variants), where it achieves 80–90%
accuracy with zero false alarms.
